# Обзор современных инструментов ИИ-разработки

Обзор актуального софта для работы с ИИ, различия между интерфейсами, особенности локальных и облачных решений.

---

## Эволюция интерфейсов: от чат-ботов к автономным агентам

В промышленной ИТ-практике формат взаимодействия со специалистом прошел путь от простых текстовых окон до автономных систем. Все инструменты на рынке делятся на три поколения:
1. **Веб-интерфейсы (ChatGPT, DeepSeek, GLM):** Изолированные диалоговые окна. Контекст передается только вручную через копипаст. Категорически не подходят для промышленной работы с кодом, логами или требованиями из-за колоссальных потерь времени на перенос данных.
2. **Классические плагины-ассистенты (Ранний GitHub Copilot, плагины для JetBrains):** Встроены в стандартные редакторы кода. Работают преимущественно в режиме автодополнения строк (inline completion) по мере ввода. Их эффективность ограничена, так как они видят только один-два открытых файла.
3. **AI-native среды разработки и CLI-агенты (Cursor IDE, Claude Code, Roo Code):** Обладают глубоким сквозным доступом к контексту всего проекта, файловой системе, терминалу и Git. Они работают в рамках *Agentic Workflow* — способны самостоятельно создавать архитектуру из множества файлов, запускать линтеры, читать логи компиляции и исправлять собственные ошибки без участия человека.

---

## Графические ИИ-среды (AI IDE)
*   **Cursor IDE:** Промышленный золотой стандарт. Это модифицированная версия VS Code, изначально спроектированная под работу с ИИ. Включает режим `Composer` (Ctrl+I), позволяющий ИИ параллельно создавать и изменять код в десятках файлов проекта, удерживая контекст всей кодовой базы благодаря фоновой векторной индексации репозитория.
*   **GitHub Copilot (в связке с VS Code):** Стандарт для крупного консервативного Enterprise-сектора (банков, корпораций). Крупный бизнес неохотно переходит на сторонние редакторы вроде Cursor из-за требований безопасности, поэтому Microsoft развивает официальный плагин, который к 2026 году также получил мощные агентские функции работы с терминалом и контекстом проекта.

### В чём главное отличие Cursor от VS Code
| VS Code | Cursor |
| :--- | :--- |
| Редактор кода | Изначально спроектирован вокруг ИИ |
| Расширяется плагинами | Понимает контекст проекта |
| ИИ — стороннее дополнение | Умеет работать с кодом на уровне файлов и логики |

Cursor становится особенно полезным, когда ты используешь его не как «генератор кода», а как инструмент разработки.

1. **Генерация кода:** Написать функцию, создать API, сгенерировать шаблон.

2. **Рефакторинг:** «Упрости код», «раздели на модули», «сделай читаемее».

3. **Анализ ошибок:** «Почему это падает?», «найди баг», «предложи исправление».

4. **Работа с архитектурой:** Обсуждение структуры, генерация интерфейсов, проверка соответствия спецификации.

## Консольные агенты (CLI) и Open-Source расширения
*   **Claude Code:** Консольный агент от компании Anthropic, работающий напрямую через терминал. У него нет графического интерфейса, он управляется командами из консоли. Ему можно отдать сложную задачу: *«Прогони тесты, найди упавший, прочитай лог ошибки в контейнере и исправь бэкенд»*. Он будет итеративно выполнять консольные команды и править код, пока задача не будет решена.
*   **Roo Code (ранее Roo Cline):** Самый популярный open-source плагин для VS Code. Его уникальность в том, что он позволяет подключить к агентскому движку **абсолютно любую модель** (включая бесплатные или локальные) и гибко настроить права доступа ИИ к вашей файловой системе и консоли.


### Как используется Claude Code

Типичный сценарий:

```bash
claude "объясни, почему падает этот сервис"
```

Или:

```bash
claude "сгенерируй функцию для обработки платежей"
```

Или даже:

```bash
cat main.py | claude "найди баги и предложи исправления"
```

То есть можно работать с файлами, пайпить данные, встраивать в скрипты. Это уже ближе к инженерии, чем к «поболтать с чатиком».

### Плюсы Claude Code

* **Гибкость:** Легко встраивается в CLI, можно автоматизировать, можно комбинировать с другими инструментами.
* **Контроль:** Ты явно задаёшь, что передаётся в контекст. Меньше «магии».
* **Скорость для опытных пользователей:** Если ты живёшь в терминале — это быстрее, чем кликать мышкой.

### Минусы Claude Code

* **Порог входа:** Если терминал для тебя — это «чёрное окно страха», будет больно.
* **Нет визуального контекста:** Не видно проект целиком, нет удобной навигации, всё нужно держать в голове.
* **Требует дисциплины:** Нужно самому управлять контекстом. Легко наделать глупостей.

### В чём ключевое отличие Claude Code от Cursor

| Критерий | Cursor                      | Claude Code                   |
| -------- | --------------------------- | ----------------------------- |
| Среда    | Визуальная IDE              | Терминал                      |
| Подход   | ИИ встроен в редактор       | ИИ как CLI-инструмент         |
| Стиль    | Работа «рядом с кодом»      | Работа «через команды»        |
| Контроль | Больше магии, меньше рутины | Меньше магии, больше контроля |

Проще: Cursor — это «разработка с ИИ в редакторе». Claude Code — это «ИИ как часть системы разработки».

::: info
**Cursor лучше, если:** вы работаете с большим проектом, важна визуальная навигация, нужен быстрый старт.

**Claude Code лучше, если:** вы любите терминал, хотите автоматизировать процессы, работаете с отдельными задачами или скриптами.
:::

Нормальная практика — использовать оба подхода: Cursor для основной разработки, Claude Code для точечных задач и автоматизации.

## Как перестать зависеть от «одной кнопки»

В какой-то момент у разработчика возникает логичный вопрос: «А что, если использовать не только встроенные модели, а что-то своё?»

И вот тут появляются сторонние модели вроде GLM.

GLM (General Language Model) — это семейство языковых моделей, разработанных компанией Zhipu AI.

По сути:

- альтернатива привычным LLM
- с похожими возможностями
- но другими характеристиками (стоимость, скорость, поведение)

GLM-модели умеют писать код, анализировать данные, работать с текстом. Это такой же «двигатель» под капотом, просто от другого производителя.

### Зачем вообще подключать сторонние модели

Причины обычно очень практичные:

- **стоимость** — иногда дешевле
- **скорость** — иногда быстрее
- **доступность** — может работать там, где другие не работают
- **эксперименты** — разные модели дают разный результат

::: success
Главное: ты перестаёшь быть привязан к одному поставщику.
:::

### Общий принцип подключения

Независимо от инструмента (Cursor или Claude Code), схема почти всегда одна:

1. Получить API-ключ у провайдера (в данном случае GLM)
2. Указать endpoint (URL API)
3. Настроить модель в инструменте
4. Использовать её как обычную LLM

Никакой магии. Просто ещё один источник «ответов».

### Подключение GLM в Cursor

Cursor изначально заточен под работу с разными моделями, так что тут всё довольно цивилизованно.
1. Откройте настройки Cursor
2. Найдите раздел, связанный с AI / Models
3. Выберите опцию добавления кастомной модели (Custom / OpenAI-compatible API)

### Что нужно указать

- **API Key** — ключ от GLM
- **Base URL** — endpoint API (предоставляется GLM)
- **Model name** — например, одна из моделей GLM

После этого модель появляется в списке и можно выбирать её для чатов и генерации.

::: warning
Cursor обычно работает с OpenAI-совместимыми API. Если GLM поддерживает такой формат — всё будет просто. Если нет — придётся использовать прокси или адаптер.
:::

### Подключение GLM в Claude Code

Здесь всё более «по-взрослому», потому что это CLI.

#### Вариант 1: через переменные окружения

```bash
export OPENAI_API_KEY=your_glm_key
export OPENAI_BASE_URL=https://api.glm-provider.com
```

Да, имя переменной может быть `OPENAI`, даже если модель не от OpenAI — жизнь полна странных решений.

#### Вариант 2: через конфигурацию

Можно указать настройки в конфиге CLI-инструмента: ключ, endpoint, модель.

### Использование

После настройки вы просто пишете:

```bash
claude "сгенерируй функцию"
```

И под капотом будет использоваться GLM вместо дефолтной модели.

### Разница в подходе

| Критерий              | Cursor                    | Claude Code     |
| --------------------- | ------------------------- | --------------- |
| Интерфейс настройки   | GUI                       | Терминал        |
| Способ                | Настройки через интерфейс | env/config      |
| Сложность подключения | Проще                     | Больше контроля |

### Подводные камни

* **Совместимость API:** Не все модели полностью повторяют OpenAI API или корректно работают «из коробки».

* **Качество ответов:** Разные модели по-разному пишут код и по-разному «понимают» задачи. Иногда дешевле — не значит лучше.

* **Контекст и ограничения:** Длина контекста, скорость, лимиты — могут отличаться довольно сильно.


::: info
Инструментов становится больше, но думать всё ещё приходится самому. ИИ можно заменить. Инженерное мышление — пока нет.
:::

## Облачные (Cloud) vs Локальные (Local) ИИ-решения

Это главный архитектурный и инфраструктурный выбор при внедрении ИИ в коммерческий контур продукта.

| Критерий | Облачные решения (Cloud API: OpenAI, Anthropic, DeepSeek) | Локальные решения (Local LLM: Llama 3, Qwen через Ollama/vLLM) |
| :--- | :--- | :--- |
| **Архитектура** | Запрос отправляется на удаленные, распределенные сервера ИИ-провайдера. | Модель разворачивается внутри закрытого контура (On-Premise) на серверах компании. |
| **Качество ответа** | **Максимальное**. Доступ к самым тяжелым, передовым коммерческим моделям-гигантам. | **Высокое/Среднее**. Напрямую зависит от мощности закупленного оборудования (модели от 8B до 70B+ параметров). |
| **Безопасность (ИБ)** | **Риск утечки данных**. Персональные данные клиентов, коммерческая тайна (NDA) и проприетарный код уходят третьим лицам. | **100% безопасность**. Данные обрабатываются внутри корпоративной сети и физически не могут покинуть периметр компании. |
| **Скорость (Latency)** | Вариативна. Зависит от загруженности серверов провайдера в пиковые часы и стабильности интернета. | Стабильно высокая. При корректной настройке инфраструктуры внутри локальной сети отклик происходит мгновенно. |
| **Стоимость** | Модель тарификации Pay-as-you-go (оплата за фактически потраченные токены). Дешево на старте, дорого при нагрузках. | Крупные вложения на старте (покупка GPU-видеокарт). Дальнейшие запросы (инференс) обходятся компании бесплатно. |



### Инструменты для локального запуска
Для работы с локальными моделями ИТ-индустрия наиболее широко использует два стандарта:
*   **Ollama:** Утилита для быстрого локального запуска и тестирования open-source моделей (*Llama 3.3*, *Qwen 2.5 Coder*, *DeepSeek-R1*) на рабочих ноутбуках специалистов «в один клик».
*   **vLLM:** Высокопроизводительный движок с открытым кодом, который разворачивается на внутренних серверах компании для быстрой и оптимизированной раздачи ИИ-модели на сотни сотрудников одновременно.

## Как этот стек применяется ИТ-специалистами разного профиля?

### Аналитику (Системному и Бизнес)
Аналитик обязан учитывать архитектуру ИИ при сборе требований и проектировании систем. Если вы работаете в регулируемых секторах (финтех, медицина, госуслуги), вы обязаны заложить в техническое задание использование **Локальной модели (Local LLM)**. Отправка конфиденциальных данных во внешние облачные API нарушает федеральные законы о персональных данных и комплаенс-политики компаний. 

### Разработчику
Вы должны владеть Cursor IDE или Claude Code для многократного ускорения написания фич и рефакторинга. При этом Middle/Senior разработчик должен уметь поднять локальную модель через `Ollama` для безопасного дебага кода локально, а также понимать, как работает движок `vLLM` на сервере для настройки бесперебойной интеграции ИИ в бэкенд приложения.

### QA-инженеру (Тестировщику)
QA тестирует стабильность и производительность ИИ-интеграций. Вы должны понимать, что локальная модель на сервере компании (например, 8-миллиардная Llama) по своему поведению отличается от облачной GPT-4: она более склонна к галлюцинациям кода и потере контекста. QA замеряет скорость генерации токенов (метрики производительности) локальной модели под высокой нагрузкой и проверяет отказоустойчивость интерфейса приложения при задержках ответов со стороны инфраструктуры.

## Шпаргалка для собеседования

* В каком случае для бизнеса целесообразнее развернуть локальную модель (Local LLM), а не использовать готовое мощное облачное API (OpenAI/DeepSeek)?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>    
Локальное решение (On-Premise) необходимо в трех сценариях:
    1. **Строгие требования ИБ и комплаенса:** когда закон или NDA запрещают передачу персональных данных и коммерческой тайны на внешние сервера.
    2. **Автономность:** система должна бесперебойно работать внутри закрытого контура компании без доступа к интернету.
    3. **Экономика на масштабе:** при миллионных потоках запросов содержание собственных серверов с GPU становится выгоднее постоянной оплаты облачных токенов.
</details>

* В чем ключевое различие между традиционными плагинами автодополнения кода (Copilot) и современными ИИ-агентами (Cursor Composer / Claude Code)?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>    
Традиционное автодополнение работает линейно в рамках одного открытого файла, подсказывая строки по мере ввода. Современные ИИ-агенты обладают контекстом всего репозитория, имеют доступ к файловой системе, Git и терминалу. Они способны самостоятельно декомпозировать сложную задачу, параллельно изменять архитектуру из множества файлов, запускать тесты в консоли и итеративно исправлять баги на основе логов компиляции.
</details>

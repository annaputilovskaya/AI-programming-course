# Архитектура интеграции: REST API, SDK и Управление сессиями

Разбор жизненного цикла ИИ-запроса, сравнение способов интеграции, реализация стриминга (SSE) для UI и архитектура сохранения контекста диалога в базе данных приложения.

## Как приложение общается с LLM: REST API vs SDK

Для интеграции ИИ в свой продукт (будь то чат-бот, автоматический генератор отчетов или модуль скоринга) приложение должно отправить запрос к удаленной языковой модели. Существует два основных инженерных пути для реализации этой связи:

### 1. Сырые HTTP-запросы (REST API)
Вы вручную формируете заголовки (включая авторизацию `Authorization: Bearer <API_KEY>`), упаковываете тело запроса в JSON и отправляете его методом `POST` на эндпоинт провайдера (например, `https://api.openai.com/v1/chat/completions`). Ключ доступа хранится на бэкенде и никогда не должен попадать в клиентский код или git-репозиторий.
* **Плюсы:** Полная независимость от языков программирования; минимальный размер итоговой сборки приложения; возможность легко переключиться на любого провайдера, поддерживающего единый стандарт (OpenAI-совместимый API).
* **Минусы:** Весь бойлерплейт-код (обработка ошибок сети, таймауты, ручная сериализация и десериализация сложных JSON) приходится писать с нуля.

### 2. Официальные библиотеки (SDK)
Провайдеры выпускают готовые обертки для популярных языков (Python, TypeScript, Go). Вместо составления HTTP-пакетов вы вызываете нативные методы: `client.chat.completions.create()`.
* **Плюсы:** Встроенная валидация типов данных из коробки; автоматические повторы запросов при сетевых сбоях (auto-retry); удобные абстракции для сложных сценариев.
* **Минусы:** Привязка к конкретной библиотеке; необходимость обновлять зависимости при выходе новых версий API провайдера.

::: warning Вопрос на собеседовании: «Если REST API и SDK дают один и тот же результат — зачем вообще SDK?» Правильный ход мысли: SDK — это не доступ к модели, а **инженерные гарантии** (типизация, retry с экспоненциальной задержкой, обработка стриминга и ошибок 429/5xx), которые в «сыром» HTTP пришлось бы реализовывать и поддерживать самому. :::

> 💡 **Как в индустрии:** большинство компаний прячут вызовы LLM за собственным API-шлюзом (прокси): приложения ходят в свой бэкенд, а он уже — в провайдера. Так централизованно управляют ключами, лимитами, fallback между моделями и учётом расходов. Пример — корпоративный LLM Gateway, через который все внутренние сервисы вызывают модели с сервисными токенами, без личных ключей в коде.

## Стриминг ответов (Server-Sent Events)

Если запрашивать ответ от ИИ обычным HTTP-запросом, пользователь столкнется с плохим UX: приложение замрет на 10–15 секунд (пока модель генерирует текст целиком), а затем мгновенно вывалит огромный блок данных. 

Чтобы интерфейс выглядел «живым», используют **стриминг** на базе протокола **Server-Sent Events (SSE)**.

::: success Как это работает: ИИ отдает ответ по кусочкам (токенам) по мере их генерации. Сервер удерживает HTTP-соединение открытым и в формате `text/event-stream` шлет события вида `data: {"delta": "кусок текста"}`, пока не получит маркер конца потока `data: [DONE]`. UI-слой приложения подхватывает эти микро-события и инкрементально рендерит текст на экране. :::

::: info Почему именно SSE, а не WebSocket: стриминг ответа модели — это односторонний поток «сервер → клиент», а SSE работает поверх обычного HTTP (не требует отдельного протокола и проброса портов, автоматически переподключается при обрыве). WebSocket нужен, только если клиенту тоже надо слать данные в реальном времени непрерывным потоком (голосовые диалоги, совместное редактирование). :::

| Тип соединения | Ожидание пользователя | Нагрузка на сеть | Подходящие сценарии |
| :--- | :--- | :--- | :--- |
| **Обычный POST** | Долгое (ожидание всего текста) | Однократный быстрый обмен | Фоновая аналитика, генерация больших PDF-отчетов, тестов. |
| **Стриминг (SSE)** | Нулевое (текст появляется сразу) | Длительное удерживание соединения | Диалоговые интерфейсы, текстовые ассистенты, live-кодинг. |

## Архитектура ролей и управление контекстом сессии

Языковые модели по своей природе являются **stateless** — они не имеют памяти. Каждый новый HTTP-запрос для них как первый в жизни. Чтобы ИИ помнил, о чем шла речь в предыдущих сообщениях, приложение обязано при каждом новом запросе передавать **всю историю диалога** заново.

Для этого используется стандартная архитектура ролей (`messages`), состоящая из трех ключевых сущностей:

1. **System (Системный промпт):** Глобальная инструкция. Задает правила игры, ограничения и характер модели. *Передается всегда самым первым элементом массива.*
2. **User (Пользователь):** Текст или медиаданные, которые вводит реальный человек в интерфейсе.
3. **Assistant (Помощник):** Предыдущие ответы самой языковой модели, которые приложение аккуратно сохранило.

> 💡 **Нюанс для сильного кандидата:** в новых API OpenAI появляется роль `developer` (замена `system` для новых моделей), а отдельная роль `tool` служит для передачи результатов вызова инструментов. Классическая триада System/User/Assistant остается базовым стандартом и индустриальным языком общения.

### Схема хранения истории диалога в Базе Данных (БД)

Чтобы реализовать полноценные сессии, в БД приложения (например, PostgreSQL) проектируются две связанные таблицы: `Sessions` (Сессии) и `Messages` (Сообщения) со связью **«Один-ко-многим» (1:M)**.

#### Таблица `Sessions`
Содержит метаданные о самой сессии общения конкретного пользователя.

| **session_id** (PK) | **user_id** | **created_at** |
| :--- | :--- | :--- |
| `uuid_1` | `usr_99` | `2026-10-27 10:00:00` |

$$\downarrow \text{Связь 1:M (У одной сессии может быть много сообщений)} \downarrow$$

#### Таблица `Messages`
Пошагово хранит каждую реплику в хронологическом порядке с обязательным указанием роли.

| **message_id** (PK) | **session_id** (FK) | **role** | **content** |
| :--- | :--- | :--- | :--- |
| `msg_101` | `uuid_1` | `system` | "Ты строгий ИТ-аналитик. Отвечай кратко" |
| `msg_102` | `uuid_1` | `user` | "Что такое REST API?" |
| `msg_103` | `uuid_1` | `assistant` | "Это архитектурный стиль взаимодействия" |
| `msg_104` | `uuid_1` | `user` | "А какие у него альтернативы?" |


**Жизненный цикл эндпоинта приложения при отправке нового сообщения:**
1. Пользователь вводит текст в чате: *«А какие у него альтернативы?»*.
2. Бэкенд вытягивает из таблицы `Messages` по текущему `session_id` все предыдущие записи, упорядоченные по времени.
3. Бэкенд формирует массив: `[msg_101, msg_102, msg_103, новое_сообщение_пользователя]`.
4. Этот массив отправляется в SDK провайдера LLM.
5. ИИ видит полную цепочку, понимает, что местоимение *«у него»* относится к *REST API*, и генерирует релевантный ответ: *«Альтернативами являются GraphQL и gRPC»*.
6. Бэкенд сохраняет новое пользовательское сообщение и ответ ИИ обратно в БД.

::: warning Вопрос безопасности: API-ключ провайдера хранится только на бэкенде (переменные окружения, secrets manager). Если ключ ушел в клиентский JS-код или в git — его нужно немедленно отозвать. :::

::: danger Ограничение контекстного окна: бесконечно копить историю в массиве нельзя. Рано или поздно массив превысит лимит токенов модели, и запрос упадет с ошибкой. Инженеры применяют тактики обрезки контекста: скользящее окно (передавать только последние N сообщений) или суммаризацию (с помощью ИИ сжимать старый диалог в один краткий системный абзац). :::

> 💡 **Лайфхак для снижения затрат:** модели с поддержкой prompt caching кэшируют неизменную «голову» запроса (system-промпт и начало истории) между вызовами, поэтому порядок сообщений не должен меняться между запросами: дописывайте новые реплики строго в конец массива.

## Зачем это знать ИТ-специалистам разного профиля?

* **Разработчику:** Вы отвечаете за корректную сборку массива ролей и интеграцию механизма стриминга на фронтенде. Вы должны закладывать алгоритмы автоматической очистки или суммаризации контекста, чтобы не тратить лишние деньги на отправку гигантских логов истории при каждом клике.
* **Аналитику:** Вы проектируете логику сессий и описываете интеграционные контракты. Вам необходимо понимать структуру ролей, чтобы правильно описывать логику поведения системы (например: «при смене темы обсуждения в UI, система должна инициировать новый `session_id` с чистой историей, но сохранить исходный `system` промпт»).
* **QA-инженеру:** Тестирование интеграции с ИИ кардинально отличается от классического тестирования API. Вы должны проверять граничные случаи: как система реагирует на обрыв стриминга (SSE) посередине слова, стирается ли контекст при закрытии сессии, и не «слепнет» ли модель, если отправить ей лог переписки из 50 сообщений за раз.

## Шпаргалка для собеседования

* В чем разница между ролями System, User и Assistant в теле запроса к языковой модели?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
<b>System</b> задает глобальный контекст, правила поведения и ограничения для модели на всю сессию. <b>User</b> — это сообщения и команды, исходящие от конечного пользователя приложения. <b>Assistant</b> — это ответы самой языковой модели, которые приложение сохраняет и отправляет обратно в ИИ для поддержания контекста и памяти в рамках stateless-архитектуры.
</details>

* Какую проблему решает технология Server-Sent Events (SSE) при интеграции ИИ в веб-интерфейсы?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
SSE решает проблему долгого ожидания ответа (плохого UX). Вместо того чтобы блокировать интерфейс на 10–20 секунд в ожидании генерации всего текста, технология позволяет серверу стримить ответ по токенам (кусочкам). Пользователь видит появление первых слов на экране мгновенно, по мере того как модель генерирует их в реальном времени.
</details>

* Как реализовать «память» ИИ-ассистента в многопользовательском приложении, если сами модели не сохраняют состояние (stateless)?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Память реализуется полностью на стороне приложения. Все сообщения (с указанием ролей user/assistant) сохраняются в реляционную или NoSQL базу данных с привязкой к уникальному идентификатору сессии (<code>session_id</code>). При каждом новом запросе бэкенд извлекает историю переписки из БД, упаковывает её в хронологический массив вместе с системным промптом и отправляет этот полный контекст в модель заново.
</details>

* Почему с ростом длины диалога интеграция с LLM становится дороже и медленнее, и как это смягчить?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Модель stateless: приложение каждый раз отправляет всю историю диалога заново, поэтому с каждым ходом растут и время обработки, и стоимость запроса (тарификация по токенам, входные токены — за всю историю). Смягчают это так: обрезка истории (скользящее окно), суммаризация старых реплик, хранение long-term контекста во внешнем векторном хранилище (RAG) вместо переписки и кэширование неизменного префикса промпта (prompt caching).
</details>

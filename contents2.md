### Блок 1: Эффективное использование AI в IDE и Git
* **Продолжительность:** 2 дня.  
* **Цель:** Автоматизация рутины, кратное ускорение написания кода и выстраивание грамотного процесса разработки без галлюцинаций ИИ.

#### Ключевые темы:
* **Интеграция ИИ в рабочий процесс:** Эффективное использование инлайн-автодополнения (Inline Completion) и чат-панелей непосредственно в редакторе кода.
* **Контекстная инженерия (Context Design):** Как правильно передавать ИИ структуру проекта, файлы разметки или документацию. Понятие **Context Window (окны контекста)** — почему нельзя «скормить» модели весь репозиторий разом и как плагины под капотом собирают контекст.
* **ИИ в терминале и Git:** Автоматизация написания понятных Git-коммитов по файлу изменений (`git diff`) в соответствии со стандартом **Conventional Commits**; автогенерация описаний для Pull Request.

> 🛠️ **Домашнее задание (микро-спринт):** Настроить ИИ-плагин в своей IDE. Взять готовый проект, с помощью ИИ сгенерировать для него конфигурационные файлы (Docker/CI-CD) и написать автоматический bash-скрипт (или использовать готовый CLI-инструмент), который анализирует изменения в Git и создает коммит с AI-описанием по стандарту.

### Блок 2: Рефакторинг, безопасность и качество кода
* **Продолжительность:** 3 дня.  
* **Цель:** Использование ИИ как независимого эксперта для проведения Code Review, поиска уязвимостей, покрытия кода тестами и документирования легаси-систем.

#### Ключевые темы:
* **Умная отладка (Debugging):** Быстрый анализ Stack Trace, логов контейнеров и сложных ошибок компиляции. Локализация багов и генерация точечных исправлений.
* **Рефакторинг без страха:** Поиск архитектурных проблем ("code smells"), оптимизация алгоритмической сложности ($O(N)$), перевод устаревшего кода на современный синтаксис.
* **Автотесты и документация:** Моментальное покрытие кода Unit-тестами (включая мокинг внешних API и обработку Edge cases). Автогенерация Swagger/OpenAPI спецификаций и Docstrings.
* **Контроль качества для собеседований:** Понятие **галлюцинаций моделей** и методы борьбы с ними при генерации тестов (обязательная валидация сгенерированного ИИ кода человеком).

> 🛠️ **Домашнее задание (микро-спринт):** Преподаватель предоставляет файл со сложной легаси-функцией, содержащей баг производительности и потенциальную уязвимость. Студент должен с помощью ИИ оптимизировать код, исправить уязвимость, сгенерировать документацию к функции и написать 3-4 Unit-теста на граничные значения.

### Блок 3: Интеграция LLM в бэкенд и обработка данных
* **Продолжительность:** 3 дня.  
* **Цель:** Научиться программно отправлять запросы к API моделей и встраивать ИИ-функции в архитектуру приложения в продакшене.

#### Ключевые темы:
* **Параметры API для продакшена:** Системные, пользовательские и ассистентские роли (System/User/Assistant), влияние параметров `Temperature` и `Max Tokens` на детерминизм и стабильность ответов.
* **Контроль формата (Structured Outputs):** Принуждение ИИ отвечать строго по заданной JSON-схеме (JSON Schema). Интеграция ответов напрямую в бэкенд без текстового парсинга.
* **Паттерн вызова функций (Function Calling / Tool Use):** Обучение модели анализировать запрос пользователя, определять необходимость вызова внешней функции и передавать туда правильные аргументы.
* **Отказоустойчивость и экономика (Критично для собеседований):** Паттерны обработки ошибок ИИ (что делать, если API недоступно, превышен лимит `Rate Limit` или модель вернула битый JSON — паттерны **Retry** и **Fallback**). Понимание стоимости запросов (**Prompt/Completion tokens**).

> 🛠️ **Домашнее задание (микро-спринт):** Написать мини-сервис (скрипт на 50–100 строк), который принимает неструктурированный текст (например: *«Забронируй стол на имя Ивана на завтра на 7 вечера»*), отправляет его в API-модели и на выходе выдает строго валидный JSON-объект вида `{ "name": "Иван", "date": "2026-10-26", "time": "19:00" }`, полностью готовый для записи в базу данных. Реализовать базовый перехват ошибок на случай сбоя API.

### Блок 4: Архитектура RAG — работа с локальной базой знаний
* **Продолжительность:** 4 дня.  
* **Цель:** Понимание современного индустриального стандарта работы с закрытыми или часто меняющимися корпоративными данными (базы знаний, регламенты, приватный код).

#### Ключевые темы:
* **Концепция RAG (Retrieval-Augmented Generation):** Зачем нужен RAG и почему он дешев. Главный вопрос собеседований: **разница между Fine-Tuning** (дообучением весов модели — дорого, долго, не гарантирует точность) и **RAG** (динамическим подкладыванием контекста в промпт — дешево, быстро, гибко).
* **Векторные эмбеддинги (Embeddings):** Перевод текста в математические векторы для семантического поиска (по смыслу, а не по точным ключевым словам).
* **Векторные базы данных:** Использование легковесных решений «из коробки» (например, ChromaDB или FAISS) для сохранения векторов и поиска по косинусному сходству.
* **Стратегии разбиения текста (Chunking):** Как правильно нарезать документацию на части, чтобы не терять смысл.

> 🛠️ **Домашнее задание (микро-спринт):** Собрать прототип «умного хелпдеска». Дан текстовый файл с внутренним регламентом компании. Написать скрипт, который разбивает регламент на чанки, преобразует их в эмбеддинги и сохраняет в локальную векторную БД. При вводе вопроса пользователя скрипт должен найти релевантные куски текста, передать их как контекст в LLM и выдать точный ответ со ссылкой на первоисточник.

# ИИ + Git: коммиты, Pull Request и ревью кода

Автоматизация Git-рутины и культура приёмки ИИ-кода: как получить осмысленные коммиты и описания PR, что проверять в диффе и где решение обязано остаться за человеком.

---

## Что делает ИИ, а что контролирует человек

Git — рутинная, но критически важная часть разработки. ИИ-ассистенты читают `git diff`, понимают логику изменений и снимают с инженера механическую работу: формулировки коммитов, черновики описаний PR, разбор больших диффов. Но именно в Git проходит граница ответственности: агент предлагает — человек принимает.

| Задача | Что делает ИИ | Что контролирует человек |
| :--- | :--- | :--- |
| **Сообщение коммита** | Читает staged-дифф, подбирает тип (`feat`, `fix`, `docs`, `refactor`) и scope. | Проверяет, что в коммит не попали временные файлы, секреты и чужие правки; что описание отражает суть. |
| **Ветка** | Создаёт ветку по шаблону команды и переносит в неё изменения. | Выбирает базовую ветку, проверяет имя и политику ветвления. |
| **Описание PR** | Агрегирует коммиты ветки в Markdown-отчёт: сводка, changelog, план тестирования. | Добавляет бизнес-контекст «зачем», убирает выдуманные утверждения, проверяет ссылки на задачи. |
| **Ревью** | Может объяснить дифф, найти подозрительные места, предложить замечания. | Принимает решение о merge, проверяет корректность, тесты, безопасность и границы задачи. |
| **Merge в общие ветки** | Готовит PR, но не сливает его. | **Только человек.** Автоматический merge ИИ-изменений в `main`/`develop` — запрещённая практика. |

Главное правило темы: **ИИ ускоряет оформление, но не отменяет приёмку.** Коммит, который «выглядит аккуратно», ещё не значит «корректен».

## Коммиты по стандарту Conventional Commits из `git diff`

ИИ-инструменты — встроенная генерация сообщения в IDE-агентах (Cursor, Copilot), CLI-утилиты вроде `aicommits`, плагины для VS Code — считывают слепок изменённого кода перед коммитом и формируют сообщение по стандарту **Conventional Commits**:

```
type(scope): description
```

Например, увидев добавление проверки домена почты в модуль авторизации, ИИ вместо «добавил проверку» выдаст:

```
feat(auth): add email domain validation for registration flow
```

Основные типы: `feat` (новая функциональность), `fix` (исправление), `docs` (документация), `refactor` (изменение структуры без изменения поведения), `test`, `chore` (сборка, зависимости), `perf`.

### Что важно проверить в сгенерированном сообщении

* **Дифф, а не намерение.** ИИ описывает то, что реально в индексе. Если вы забыли `git add` часть файлов или, наоборот, добавили лишнее — сообщение будет честным описанием неправильного коммита.
* **Один коммит — одно изменение.** Агент любит складывать в один коммит фичу, рефакторинг и переформатирование. Разделяйте: `git add -p` и отдельные коммиты дешевле, чем разбор общего диффа на ревью.
* **Секреты и мусор.** Перед коммитом проверьте `.env`, дампы, логи, локальные конфиги IDE. Сканер секретов в pre-commit (см. блок 2, тема 7) надёжнее внимательности.
* **Сгенерированные файлы.** `package-lock.json`, миграции, сборки — либо в отдельном коммите, либо исключены правилами. Иначе шум в диффе прячет смысловые правки.

### Конвенция проекта важнее «дефолтного» стандарта

Conventional Commits — не единственный стандарт. В командах встречается формат «ключ задачи из таск-трекера + краткое описание» (`PROJ-142 add retry for payment API`), и тогда правило проекта приоритетнее канонического вида. То же с ветками: агент может создать `feature/PROJ-142-payment-retry` по шаблону команды, но политику ветвления (от какой ветки, куда мержить, нужен ли rebase) задаёт человек и файл правил проекта.

Практический вывод для собеседования: **стандарт — это конфигурируемое правило проекта, а не догма.** Хороший ответ звучит так: «смотрю, что принято в репозитории; если есть `CONTRIBUTING.md` или правила в `.cursor/rules`/`AGENTS.md` — следую им, а не тому, что модель считает правильным по умолчанию».

## Описание Pull Request

Когда изменения отправлены в удалённую ветку, ИИ собирает разницу между ветками и готовит структурированное саммари для ревьюера:

* **Summary** — что сделано и зачем, в двух-трёх предложениях.
* **Changelog** — пофайловый разбор ключевых правок.
* **Testing Plan** — что и как проверять: команды, сценарии, ожидаемый результат.

### Чего в описании PR быть не должно

| Плохо | Почему | Как правильно |
| :--- | :--- | :--- |
| «Все тесты проходят» без вывода и команд | Непроверяемое утверждение; агент мог не запускать тесты вовсе | Указать команду и результат: `npm test — 42 passed`, ссылка на CI-прогон |
| Выдуманные тесты и сценарии | ИИ «дописывает» проверки, которых не было; ревьюер теряет время | Перечислять только реально добавленные тесты и реально выполненные проверки |
| «Всё протестировано вручную» | Нет доказательств и границ проверки | «Проверено: регистрация с новым доменом; не проверялось: SSO» |
| Ссылки на несуществующие тикеты и документы | Ломают трассируемость | Ссылки копируются из задачи, а не генерируются |
| Маркетинговые формулировки («значительно улучшено») | Скрывают реальный объём изменений | Конкретика: «задержка снижена с 800 до 120 мс на синтетическом наборе» |

Описание PR — это не реклама изменения, а **инструкция для проверяющего**. Чем честнее указаны границы проверки, тем быстрее и безопаснее ревью.

## Ревью ИИ-кода: чек-лист

ИИ-код нельзя принимать «по ощущению гладкости». Проверка идёт по шести направлениям, и каждое имеет типовой красный флаг.

| Направление | Вопрос ревьюера | Красный флаг |
| :--- | :--- | :--- |
| **Корректность** | Код делает то, что заявлено, на всех ветках? | Обработаны только happy path; граничные значения не учтены |
| **Соответствие задаче** | Изменено ровно то, что просили? | Правки в файлах и модулях вне постановки |
| **Тесты** | Новые тесты действительно проверяют поведение? | `expect(result).toBeDefined()`, тесты «под моки», нет негативных сценариев |
| **Обработка ошибок** | Что будет при `null`, таймауте, 500 от API? | Исключения проглатываются, ошибка не логируется, retry без ограничения |
| **Безопасность** | Нет секретов, инъекций, лишних прав? | Конкатенация SQL, `eval`, токен в коде, новый доступ к файлам/сети |
| **Читаемость** | Смогут ли это поддерживать без автора и без ИИ? | Дублирование, «магические» имена, комментарии, противоречащие коду |

Отдельно проверяйте **реальность API**: методы, библиотеки и флаги, которые «уверенно» использует модель, должны существовать в вашей версии зависимости. Галлюцинированный метод компилятор поймает не всегда — в динамических языках он проявится только в рантайме.

Если агент работает через подключённые инструменты, в дифф попадает и конфигурация доступа: новый MCP-сервер, расширенные права, дополнительные источники данных. Это такой же объект ревью, как код, — новый канал к файлам, базе или внешнему API. Как устроен MCP и какие риски с ним связаны — блок 3, тема 3.

### Почему «уверенный, но неверный» дифф опаснее очевидной ошибки

Очевидная ошибка — синтаксис, падающий тест, несуществующий импорт — останавливает конвейер и заставляет разобраться. Опаснее дифф, который **выглядит правильным**: аккуратно отформатирован, снабжён логичными комментариями, проходит тесты, но меняет поведение в редком сценарии или молча удаляет проверку, которую модель сочла «избыточной».

Причина — в психологии восприятия: красивый код получает «кредит доверия», и ревьюер читает его как подтверждение, а не как гипотезу. Поэтому в ревью ИИ-кода действует правило: **сначала спросите, что изменилось в поведении, и только потом — как это написано.** Ответ на первый вопрос даёт дифф и тесты, а не стиль.

## Scope creep: как ловить «попутные» правки

Scope creep — самая частая проблема ИИ-агентов. Поставили задачу «добавить валидацию телефона», а в диффе оказались переименованные переменные, переформатированные файлы и «улучшенная» обработка ошибок в трёх соседних модулях. Формально всё работает, фактически — ревью превращается в разбор чужого рефакторинга.

**Протокол контроля границ задачи:**

1. **До запуска агента** зафиксируйте список файлов и модулей, которые разрешено менять. В инструкциях проекта это формулируется явно: «работай только в `src/validation/phone.ts`, не трогай остальные файлы».
2. **После генерации** сравните дифф с постановкой: `git diff --stat` показывает файлы и объём правок за секунды.
3. **Правки вне задачи** — не «бонус», а дефект процесса: откатите их или вынесите в отдельный коммит/PR с собственным обоснованием.
4. **Рефакторинг — отдельно.** Смешивать «изменение поведения» и «изменение структуры» в одном коммите нельзя: тогда непонятно, что именно сломало тест.
5. **Проверяйте whitespace-правки.** `git diff -w` игнорирует пробелы; если diff «исчез» — изменение было чисто форматным, и ему не место в коммите с логикой.

> **Мини-кейс.** Агент получил задачу «поправить опечатку в сообщении об ошибке». В ответ он переформатировал 40 файлов: настроил отступы, разбил длинные строки, переставил импорты. CI зелёный, тесты проходят. На ревью это видно за десять секунд: `git diff --stat` показывает 40 файлов вместо одного, а `git diff -w` — что содержательная правка ровно одна. Дальше два действия: откатить форматирование (`git checkout -- .` с последующим повторным применением точечной правки) и добавить в правила проекта запрет на массовое переформатирование. Если формат действительно нужен — он делается отдельным PR, который ревьюится по своим правилам.

## Откат: `revert` против `reset`

Ошибки в ИИ-коммитах случаются, и цена ошибки зависит от того, куда коммит уже уехал.

| Ситуация | Инструмент | Что происходит | Когда использовать |
| :--- | :--- | :--- | :--- |
| Коммит только локально, ещё не запушен | `git reset --soft HEAD~1` / `--mixed` | История переписывается, изменения остаются в индексе/рабочей копии | Исправить сообщение или пересобрать коммит |
| Коммит локально, правки не нужны | `git reset --hard HEAD~1` | Коммит и изменения удаляются | Только если уверены: несохранённые правки пропадут |
| Коммит уже в общей ветке | `git revert <sha>` | Создаётся новый коммит, отменяющий изменения | Безопасный путь: история не переписывается |
| Нужно убрать правки, но оставить файлы | `git restore <file>` / `git restore --staged <file>` | Откат рабочей копии или индекса | Локальная уборка перед коммитом |
| В коммит попал секрет | Сначала **ротация ключа**, затем `revert`; переписывание истории — только по согласованию с командой | Ключ считается скомпрометированным навсегда | Немедленно, не дожидаясь ревью |

**Почему `revert`, а не `reset`, для общих веток.** `reset` переписывает историю: у коллег остаются коммиты, которых «больше нет», и следующий `pull` превращается в конфликт. `revert` добавляет обратную операцию — история остаётся линейной и понятной, а факт отката виден в логе.

**Force-push в общую ветку** допустим только в исключительных случаях (утечка секрета, гигантский бинарник) и только с предупреждением команды. Для ИИ-агента это действие должно быть запрещено правилами: агент не переписывает историю и не мержит в `main`.

## Зачем это знать ИТ-специалистам разного профиля?

* **Разработчику:** Вы перестаёте писать «fix» и «update», но именно вы отвечаете за то, что в коммит не попал мусор, а в PR — выдуманные тесты. Чек-лист ревью и разбор диффа — ваша ежедневная практика, а не формальность.
* **Аналитику:** Вы формулируете постановку так, чтобы её можно было проверить по диффу: какие файлы меняются, что считается готовым, какие сценарии обязательны. Описание PR и changelog становятся языком отчётности перед бизнесом — но только если в них нет непроверяемых обещаний.
* **QA-инженеру:** Вы проверяете не только продукт, но и сам процесс приёмки: есть ли тесты на исправленный кейс, не изменилось ли поведение «попутно», воспроизводится ли заявленный в PR план тестирования. Умение найти scope creep в диффе — такой же навык, как найти баг в приложении.

## Шпаргалка для собеседования

* Как ИИ помогает автоматизировать Git и что при этом остаётся за человеком?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
ИИ читает <code>git diff</code>, подбирает тип и scope для Conventional Commits, готовит черновик описания PR (summary, changelog, план тестирования) и может создать ветку по шаблону команды. За человеком остаются: проверка состава коммита (секреты, временные файлы, чужие правки), бизнес-контекст, решение о merge и любое переписывание общей истории. Merge в общие ветки — только вручную.
</details>

* Что проверять при ревью кода, сгенерированного ИИ?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Шесть направлений: корректность на всех ветках, соответствие постановке (нет правок вне задачи), качество тестов (реальные assertions, негативные сценарии), обработка ошибок и граничных значений, безопасность (секреты, инъекции, лишние права), читаемость и поддерживаемость. Отдельно — существование всех использованных API и библиотек в вашей версии. Решение принимается по диффу и запущенным проверкам, а не по гладкости текста.
</details>

* Почему «уверенный, но неверный» дифф опаснее очевидной ошибки?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Очевидная ошибка останавливает сборку или тесты и заставляет разобраться. Уверенный дифф выглядит аккуратно, снабжён комментариями и часто проходит тесты, но меняет поведение в редком сценарии или молча удаляет проверку. Красивый код получает кредит доверия, и ревьюер читает его как подтверждение, а не как гипотезу. Поэтому сначала выясняют, что изменилось в поведении, и только потом оценивают стиль.
</details>

* Что такое scope creep и как его поймать на ревью?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Scope creep — «попутные» правки вне постановки: переформатирование, переименования, рефакторинг соседних модулей. Ловится сравнением диффа с задачей: <code>git diff --stat</code> показывает файлы и объём, <code>git diff -w</code> отделяет форматирование от смысловых правок. Профилактика: заранее ограничить список файлов в правилах проекта, рефакторинг выносить в отдельный коммит/PR, правки вне задачи откатывать.
</details>

* Коммит с ошибкой уже в общей ветке. `revert` или `reset` — и почему?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Для общей ветки — <code>git revert</code>: он создаёт новый коммит с обратными изменениями и не переписывает историю, поэтому у коллег не ломается <code>pull</code>. <code>git reset</code> переписывает историю и допустим только локально, до push. Если в коммит попал секрет, сначала ротируется ключ, затем делается revert; переписывание истории (filter-repo/BFG) — только по согласованию с командой.
</details>

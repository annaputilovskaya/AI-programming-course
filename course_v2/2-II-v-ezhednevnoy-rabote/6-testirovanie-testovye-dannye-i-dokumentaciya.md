# Тестирование, тестовые данные и документация с ИИ

Генерация unit-тестов, моков и документации, проверка их качества и подготовка тестовых данных: как не принять «зелёные, но пустые» тесты и как тестировать код, внутри которого вызывается недетерминированная модель.

---

## Unit-тесты с моками и edge cases

Написание тестов — классическая задача, на которую у команд «не хватает времени». ИИ снимает механическую часть, если задать ему рамки:

* **Happy path vs edge cases:** на каждый позитивный сценарий просите минимум 3–4 негативных — `null`, пустая строка, слишком длинное значение, спецсимволы, падение сети.
* **Изоляция через моки:** если метод ходит в базу или внешнее API, ИИ сгенерирует заглушки, чтобы тест оставался быстрым и детерминированным.
* **Явные требования к оформлению:** фреймворк, структура `describe`/`it`, где настраиваются моки, что именно проверять. Без этого модель выдаст «тест ради теста».

### Практический кейс: промпт для генерации тестов с моками (Jest / TypeScript)

Представим сервисный метод, который запрашивает баланс пользователя из внешней платёжной системы и сохраняет лог в базу:

```typescript
// orderService.ts
export async function processUserPayout(userId: string, amount: number, paymentApi: any, db: any) {
  if (amount <= 0) throw new Error("Invalid amount");
  
  const balance = await paymentApi.getUserBalance(userId);
  if (balance < amount) throw new Error("Insufficient funds");
  
  const transactionId = await paymentApi.charge(userId, amount);
  await db.logs.create({ userId, transactionId, status: "SUCCESS" });
  
  return transactionId;
}
```

Если просто попросить ИИ *«напиши тесты»*, он проигнорирует изоляцию и edge cases. Чтобы получить качественный результат, используйте **структурированный промпт-шаблон**:

> **Промпт для ИИ:**
> Напиши модульные тесты на фреймворке Jest для функции `processUserPayout` из файла `orderService.ts`. 
> 
> **Требования к оформлению:**
> 1. Полностью изолируй внешние зависимости `paymentApi` и `db` с помощью `jest.fn()` моков. Настрой их дефолтное поведение в `beforeEach`.
> 2. Сгруппируй тесты через блоки `describe` («Happy Path» и «Edge Cases & Errors»).
> 
> **Сценарии для проверки:**
> * **Happy Path:** Успешное списание при достаточном балансе. Проверь, что `db.logs.create` был вызван с правильными аргументами.
> * **Edge Case 1:** Передача `amount <= 0` (должна быть ошибка "Invalid amount", а моки API не должны вызываться).
> * **Edge Case 2:** Недостаточно средств на балансе (ошибка "Insufficient funds", метод `paymentApi.charge` не должен быть вызван).
> * **Edge Case 3:** Внешнее API упало с ошибкой сети (проверь проброс исключения).

**Результат генерации ИИ по требованиям:**

```typescript
import { processUserPayout } from "./orderService";

describe("processUserPayout", () => {
  let mockPaymentApi: any;
  let mockDb: any;

  beforeEach(() => {
    // Настраиваем чистые моки перед каждым тестом
    mockPaymentApi = {
      getUserBalance: jest.fn().mockResolvedValue(1000),
      charge: jest.fn().mockResolvedValue("tx_123"),
    };
    mockDb = {
      logs: { create: jest.fn().mockResolvedValue(true) },
    };
  });

  describe("Happy Path", () => {
    it("should successfully process payout and log transaction", async () => {
      const result = await processUserPayout("user_1", 200, mockPaymentApi, mockDb);

      expect(result).toBe("tx_123");
      expect(mockPaymentApi.getUserBalance).toHaveBeenCalledWith("user_1");
      expect(mockPaymentApi.charge).toHaveBeenCalledWith("user_1", 200);
      expect(mockDb.logs.create).toHaveBeenCalledWith({
        userId: "user_1",
        transactionId: "tx_123",
        status: "SUCCESS",
      });
    });
  });

  describe("Edge Cases & Errors", () => {
    it("should throw error if amount is zero or negative", async () => {
      await expect(processUserPayout("user_1", 0, mockPaymentApi, mockDb))
        .rejects.toThrow("Invalid amount");
      
      // Проверяем, что до внешних вызовов дело не дошло
      expect(mockPaymentApi.getUserBalance).not.toHaveBeenCalled();
    });

    it("should throw error if user has insufficient funds", async () => {
      mockPaymentApi.getUserBalance.mockResolvedValue(50); // Баланс меньше списания

      await expect(processUserPayout("user_1", 100, mockPaymentApi, mockDb))
        .rejects.toThrow("Insufficient funds");

      expect(mockPaymentApi.charge).not.toHaveBeenCalled();
      expect(mockDb.logs.create).not.toHaveBeenCalled();
    });

    it("should propagate network errors from payment API", async () => {
      mockPaymentApi.getUserBalance.mockRejectedValue(new Error("Network Error"));

      await expect(processUserPayout("user_1", 100, mockPaymentApi, mockDb))
        .rejects.toThrow("Network Error");
    });
  });
});
```

Обратите внимание: качественный результат получился не потому, что модель «умная», а потому что в промпте перечислены **конкретные сценарии и проверки**. Тот же приём работает и с покрытием: просите не «покрой тестами», а «перечисли ветки и границы, затем тест на каждую».

### «Зелёные» тесты не значит хорошие: аудит сгенерированных тестов

Даже выполненный по всем правилам ИИ-генерат даёт **черновик**, а не готовые тесты. Сам протокол приёмки сгенерированного кода — проверка реальности API, статический анализ, прогон тестов, чтение диффа и независимое подтверждение — разобран в блоке 2, теме 5 (Verification-First); здесь мы разбираем только специфику тестов. Исследования качества LLM-тестов стабильно показывают: тесты запускаются, но часто содержат **слабые проверки** (weak assertions) — код покрыт, а реальные баги такие тесты не ловят. Признаки «мёртвого» теста:

* проверяется только вызов функции, но не значение результата (`expect(result).toBeDefined()` вместо сравнения с конкретным значением);
* моки настроены так, что тест перестаёт зависеть от реальной логики («тест моков вместо теста кода»);
* все сценарии — вариации happy path; ветки ошибок не покрыты;
* тест проходит и при заведомо сломанной реализации.

**Мутационное тестирование (mutation testing)** — объективный способ аудита. Инструмент (Stryker для JS/TS, mutmut для Python, PIT для Java) вносит в код мелкие «поломки»-мутанты (меняет `<` на `<=`, удаляет вызов функции) и проверяет: поймут ли это ваши тесты? Тест, который «зелёный» и после поломки кода, не проверяет ничего.

**Промпт-аудит для ИИ (дешёвая альтернатива, когда мутационного инструмента в проекте нет):**

> *«Вот код функции и её тесты. Сымитируй мутационное тестирование: предложи 5 мелких изменений кода (мутантов), которые тесты НЕ заметят. По каждому — какое утверждение (assertion) нужно добавить, чтобы мутант был "убит"».*

**Интерпретация:** выжившие мутанты — это конкретные «слепые зоны» тестов, а не общий балл качества. Каждый выживший мутант = инструкция, какое поведение тесты не фиксируют.

## Тестовые данные

Тестовые данные — половина качества тестов. Плохой набор делает бессмысленной даже идеальную логику: если все пользователи «Иван», все суммы положительные, а строки — латиница, граничные дефекты просто не проявятся.

### Синтетика вместо продакшена

Правило простое: **в тестах и в промптах к ИИ нет реальных персональных данных.** Вместо выгрузки из прода — синтетические сущности:

| Плохо | Хорошо |
| :--- | :--- |
| `Иван Петров, +7 999 123-45-67, ivan@company.ru` | `user_id_1`, `test@email.local`, `+7 000 000-00-01` |
| Реальный номер карты и паспорта | `4111 1111 1111 1111` (тестовый номер платёжной системы), `passport_placeholder` |
| Прод-дамп «только посмотреть, как ведёт себя баг» | Обезличенная выборка, собранная по тем же признакам, что и баг |

Почему нельзя брать прод-выгрузку «только посмотреть»:

* она оседает в локальных файлах, кэшах, бэкапах и истории чатов — и живёт там дольше, чем задача;
* её легко отправить в ИИ-ассистента «для контекста» — вместе с ПДн и коммерческой тайной (см. блок 2, тему 7);
* удалить данные из всех копий практически невозможно, а инцидент уже произошёл в момент копирования;
* обезличивание «на глаз» (убрать имя) не работает: по сочетанию пола, возраста, города и даты человек восстанавливается.

### Фабрики, фикстуры и seed-данные

* **Фабрики** создают объект с валидными значениями по умолчанию и позволяют переопределить только нужное поле: `createUser({ status: "blocked" })`. Это убирает дублирование и делает тест читаемым.
* **Фикстуры** — стабильные эталонные данные (JSON, CSV, ответы API), хранящиеся в репозитории. Подходят для контрактных тестов и воспроизведения инцидентов.
* **Seed-данные** заполняют базу для интеграционных тестов. Детерминированный генератор (faker с фиксированным seed, а не `random`) гарантирует, что тест не «мигает» от прогона к прогону.
* **Изоляция:** каждый тест создаёт своё состояние или откатывается транзакцией. Общая база между тестами — источник плавающих падений и ложных «зелёных».

### Граничные наборы

Минимальный набор, который стоит прогонять через любую функцию, работающую с текстом и числами:

| Категория | Примеры | Что ловит |
| :--- | :--- | :--- |
| **Пустота** | `null`, `undefined`, `""`, пустой массив, `{}` | Отсутствие проверок, падения на `.length`/`.map` |
| **Границы чисел** | `0`, `-1`, `MAX_INT`, `0.1 + 0.2` | Ошибки округления, переполнение, деление на ноль |
| **Длина строки** | 0, 1, лимит, лимит + 1, 100 000 символов | Обрезка, `varchar(n)`, таймауты, память |
| **Юникод и эмодзи** | `Å`, `漢字`, `👍🏽`, составные эмодзи | Побайтовые операции, `length` вместо `grapheme count` |
| **RTL и смешанные направления** | `مرحبا`, строка с RTL + латиницей | Отображение, сортировка, регулярные выражения |
| **Спецсимволы и разметка** | `<script>`, `%`, `_`, `'`, `--` | XSS, SQL-инъекции, шаблонизаторы, LIKE |
| **Форматы и локали** | `01.02.2026` vs `02/01/2026`, часовые пояса | Неверная интерпретация дат |
| **Дубликаты** | Два одинаковых ID, повторный запрос | Идемпотентность, уникальные индексы |

## Тесты для недетерминированных ИИ-функций

Код, внутри которого вызывается LLM, нельзя тестировать «как обычную функцию»: ответ меняется от прогона к прогону, а `temperature: 0` не гарантирует побайтовой воспроизводимости. Граница простая: **тестируем то, что детерминировано, и оцениваем то, что нет.**

### Мок модели для unit-тестов

В unit-тестах бизнес-логики модель заменяется моком с фиксированным ответом:

* мок возвращает заранее заданный JSON или текст — проверяется обработка: парсинг, валидация, запись в БД, сообщение пользователю;
* отдельные тесты — на «плохие» ответы мока: пустой ответ, обрезанный JSON, отказ модели, таймаут, 429;
* мок фиксирует **аргументы вызова**: какой промпт, какие инструменты, сколько токенов запрошено. Это позволяет поймать регрессию в сборке промпта, не завися от качества модели.

### Контрактные тесты на структуру, а не на текст

Для функции, которая должна вернуть структурированный ответ, тест проверяет **схему**, а не формулировку:

* ответ валиден по JSON Schema: обязательные поля, типы, `enum`, допустимые диапазоны;
* значения прошли бизнес-валидацию (например, `status` из разрешённого списка, сумма не отрицательна);
* при невалидном ответе сработал retry/fallback, а не исключение наружу.

Такие тесты стабильны: они не ломаются от того, что модель переформулировала фразу. Для проверки самой структуры можно использовать тот же валидатор схемы, что и в рантайме, — это заодно гарантирует, что тест и продакшен проверяют одинаковые правила.

### Snapshot-тесты и почему они хрупкие

Snapshot фиксирует полный вывод и сравнивает его с эталоном. Для LLM-ответов это плохой основной инструмент:

* любая переформулировка — «падение», хотя поведение корректно; команда привыкает обновлять снапшоты не глядя;
* снапшот не объясняет, **что именно** сломалось: изменение в одном слове и потеря смысла выглядят одинаково;
* он не проверяет требования — только факт совпадения.

Допустимое применение: снапшоты для **промпта** (сборка сообщений, порядок частей, подстановка переменных) и для детерминированных частей пайплайна — там они полезны и стабильны. Ответ модели оценивается другими средствами.

### Где проходит граница

| Что проверяем | Инструмент | Где разобрано |
| :--- | :--- | :--- |
| Правильно ли собран промпт и вызван инструмент | Unit-тест с моком модели, проверка аргументов | Здесь |
| Соответствует ли ответ схеме и бизнес-правилам | Контрактный тест, валидатор JSON Schema | Здесь |
| Корректен ли текст ответа, нет ли галлюцинаций | Golden set, LLM-as-judge, ручная разметка | Блок 3, тема 6 |
| Устойчиво ли приложение к инъекциям и злоупотреблениям | Red teaming, негативные сценарии | Блок 3, тема 4 |
| Насколько хорош поиск RAG | Recall@K, MRR, golden set для чанкинга | Блок 4, тема 3 |

::: warning Не путайте уровни
«Функция вызвана правильно» и «ответ качественный» — разные утверждения. Первое проверяется обычными тестами и не требует дорогих прогонов; второе — оценкой на наборе примеров, и она стоит денег. Смешивание этих задач приводит к медленным и хрупким тестам, которые всё равно не отвечают на вопрос о качестве.
:::

## Документация

### Docstrings и Swagger/OpenAPI

* **Кодовая документация:** ИИ за один промпт снабжает функции комментариями (JSDoc, Python docstrings) с описанием аргументов, типов и возвращаемых значений.
* **API-документация:** передав ИИ код контроллеров или DTO (Data Transfer Objects), можно получить схему **Swagger/OpenAPI** в YAML/JSON.
* **Контроль качества:** сгенерированная документация проверяется тем же протоколом, что и код. ИИ может «документировать» поведение, которого нет (например, приписать функции обработку `null`). Для OpenAPI валидируйте схему линтером (Spectral, `openapi-spec-validator`) — это ловит структурные ошибки автоматически.

### README, ADR и changelog

Три документа, которые ИИ пишет хорошо — и которые чаще всего отсутствуют:

* **README** — что это за проект, как запустить, какие переменные окружения нужны, как прогнать тесты. Идеальный промпт: «сгенерируй README по структуре репозитория и `package.json`, не выдумывай команды, которых нет».
* **ADR (Architecture Decision Record)** — короткая запись решения: контекст, варианты, выбранный вариант, последствия. ИИ удобно использовать как черновик: он восстановит альтернативы по диффу и обсуждению, но решение и его обоснование подтверждает человек.
* **Changelog** — генерируется из истории коммитов по Conventional Commits (см. блок 2, тему 4). Важно проверять, что в «Added/Fixed» не попали внутренние правки, не влияющие на пользователя, и не потерялись изменения поведения.

### Проверка документации на расхождение с кодом

Документация устаревает быстрее кода, а ИИ-сгенерированная — особенно, потому что выглядит убедительно. Практики, которые ловят расхождение автоматически:

1. **Примеры из документации выполняются в CI** — как тесты. Если команда из README перестала работать, сборка падает.
2. **Контрактные тесты против OpenAPI-схемы** — реальные ответы API валидируются по опубликованной спецификации.
3. **Линтеры и линковка** — Spectral для схем, markdown-link-check для ссылок, проверка версий в примерах.
4. **Docs-as-code** — документация меняется в том же PR, что и код; ревьюер проверяет оба артефакта.
5. **Периодический аудит ИИ** — «сравни README с фактическими командами в `Makefile` и `package.json`, перечисли расхождения». Это дешёвый способ найти устаревшее, но результат всё равно проверяется запуском.

## Зачем это знать ИТ-специалистам разного профиля?

* **Разработчику:** Вы избавляетесь от синдрома «чистого листа» при написании тестов и документации, но обязаны следить, чтобы тесты не «зеленели» из-за слабых assertions и моков. Навык готовить тестовые данные и мокать модель отличает инженера, который умеет тестировать ИИ-код, от того, кто тестирует только обычный.
* **Аналитику:** Вы задаёте контракт до кода: OpenAPI-схема, набор тестовых данных и граничные сценарии — часть требований, а не «дело разработчика». Синтетические данные и явные границы (пусто, максимум, юникод) снимают часть вопросов ещё на согласовании.
* **QA-инженеру:** Вы аудируете сгенерированные тесты (мутационное тестирование, проверка assertions), проектируете тестовые наборы и отделяете проверку структуры от оценки качества ответа. Понимание, что мок модели проверяет вызов, а не интеллект, помогает не создавать ложное чувство покрытия.

## Шпаргалка для собеседования

* Как ИИ помогает в генерации unit-тестов и можно ли ему полностью доверять этот процесс?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
ИИ автоматизирует рутину: бойлерплейт, настройку фреймворка, моки, негативные сценарии — если в промпте перечислены конкретные проверки. Доверять полностью нельзя: модель склонна к happy path и слабым assertions, а моки могут маскировать проблемы архитектуры. Задача инженера — задать сценарии, проверить, что тесты падают на сломанном коде, и оценить покрытие веток и границ.
</details>

* Почему «зелёные» тесты не значит хорошие и что такое мутационное тестирование?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Зелёный тест может ничего не проверять: <code>toBeDefined()</code> вместо сравнения значения, моки вместо логики, только happy path. Мутационное тестирование вносит в код мелкие дефекты-мутанты и смотрит, ловят ли их тесты. Выживший мутант — конкретная слепая зона: поведение, которое тесты не фиксируют. Это объективный аудит, в отличие от процента покрытия.
</details>

* Какие тестовые данные допустимо использовать и почему нельзя брать прод-выгрузку «только посмотреть»?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Только синтетические или обезличенные данные: <code>user_id_1</code>, <code>test@email.local</code>, тестовые номера карт. Прод-выгрузка оседает в локальных файлах, кэшах, бэкапах и чатах с ИИ; её легко отправить во внешнюю модель вместе с ПДн; удалить все копии практически невозможно, а инцидент происходит уже в момент копирования. Обезличивание «на глаз» не работает — по комбинации признаков человек восстанавливается.
</details>

* Как тестировать функцию, внутри которой вызывается LLM?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Разделить детерминированное и недетерминированное. В unit-тестах модель заменяется моком с фиксированным ответом: проверяются парсинг, валидация, бизнес-логика, обработка таймаутов и битого JSON, а также аргументы вызова (какой промпт и инструменты переданы). Структура ответа проверяется контрактным тестом по JSON Schema, а не сравнением текста. Snapshot-тесты для ответов хрупкие — их место в проверке сборки промпта. Качество самого ответа — отдельная задача оценки (блок 3, тема 6).
</details>

* Как быстро спроектировать или задокументировать REST API с помощью ИИ?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
Передать ИИ модели данных или код контроллеров и попросить OpenAPI-схему в YAML/JSON; либо наоборот — из требований аналитика получить черновик спецификации, согласовать её и только потом генерировать каркас. Обязательна валидация схемы линтером (Spectral, openapi-spec-validator): ИИ может описать несуществующие поля и коды ответов. Примеры из документации стоит прогонять в CI, иначе схема быстро разойдётся с кодом.
</details>

* Какие документы, кроме docstrings и OpenAPI, стоит поручать ИИ и как проверить их актуальность?
<details>
<summary><b>👉 Посмотреть правильный ответ</b></summary>
README (запуск, переменные окружения, тесты), ADR (контекст решения, альтернативы, последствия) и changelog из Conventional Commits. ИИ даёт черновик, человек подтверждает факты. Актуальность проверяется автоматически: примеры из README выполняются в CI, ответы API валидируются по OpenAPI, схемы и ссылки проверяются линтерами, документация меняется в том же PR, что и код.
</details>

# ИИ для ИТ-специалистов: обновлённое оглавление (v2)

**Для кого:** студенты направлений «Разработка», «QA», «Аналитика».  
**Цель:** практические ИИ-компетенции и уверенность на собеседовании.  
**Формат:** 4 блока, 21 тема; нумерация сквозная только внутри блока, каждая тема — до 30 минут.  
**Статус:** черновик оглавления. Пулы вопросов и домашние задания ведутся отдельно.

---

## Блок 1. Как работают LLM, инструменты и промпт-инжиниринг — 3 дня (без изменений)

1. **Эволюция от машинного кода к ИИ-разработке.** ИИ-программирование vs вайб-кодинг. Почему навык управления ИИ сегодня критически важен.
   - *О чем:* Вводная лекция о смене парадигмы в IT, разнице между хаотичным использованием нейросетей («вайб-кодинг») и системным инженерным подходом.

2. **Устройство LLM на уровне практика.** Токены, контекстное окно, природа галлюцинаций, temperature и детерминизм. Почему модель «не знает» ваш код и данные по умолчанию.
   - *О чем:* Технические ограничения моделей, математика токенов, почему нельзя загрузить огромный проект целиком и как настройки креативности влияют на результат.

3. **Базовые техники промптов и управление контекстом.** Роль, контекст, few-shot примеры, декомпозиция сложной задачи, итеративное уточнение.
   - *О чем:* Правила составления запросов для получения предсказуемых ответов, управление контекстом ИИ-ассистента для точного удержания задачи.

4. **Структурированный вывод.** Получение JSON/Markdown/SQL по схеме, валидация ответа, действия при невалидном или неполном результате.
   - *О чем:* Как заставить ИИ отдавать ответы в строгом машиночитаемом формате для дальнейшей автоматизации и что делать, если ИИ нарушил структуру.

5. **Границы применения ИИ.** Детерминированные vs генеративные задачи, цена ошибки, где ИИ только мешает. Умение сказать «здесь ИИ не нужен».
   - *О чем:* Критический анализ задач. Определение зон, где классический алгоритм эффективнее, дешевле и надежнее, чем нейросеть.

## Блок 2. ИИ в ежедневной работе: IDE-агенты, Git, качество и безопасность кода — 3–4 дня

1. **Обзор современных инструментов ИИ-разработки.** Cursor IDE, Claude Code, сторонние модели и локальные решения. Как выбирать инструмент, а не зависеть от одной кнопки.
   - *О чем:* ландшафт AI IDE и CLI-агентов, различия интерфейсов, локальные и облачные решения, критерии выбора под задачу.

2. **Первичная настройка и спецификации.** Почему настройка среды — основа нормальной работы. `AGENTS.md`, `.cursor/rules`, `CLAUDE.md`: как задать правила проекта, если ТЗ не существует.
   - *О чем:* подготовка рабочего пространства, файлы инструкций для ИИ, инициализация проекта при дефиците вводных данных.

3. **IDE-ассистенты и контекстная инженерия.** Автодополнение, чат, Plan/Agent; сбор контекста; принцип «ИИ пишет — человек проверяет»; контроль и дебаг работы ИИ.
   - *О чем:* практическая работа с кодом и документами в реальном времени, управление файловым контекстом, методы отслеживания и исправления ошибок за ИИ.

4. **ИИ + Git: коммиты, Pull Request и ревью кода.** Conventional Commits из `git diff`, описания PR, чек-лист ревью ИИ-кода, контроль scope creep и откат.
   - *О чем:* автоматизация Git-рутины и культура приёмки ИИ-кода: что проверять, что остаётся за человеком, как не принять «уверенный, но неверный» дифф.

5. **Отладка и рефакторинг с ИИ.** Разбор стектрейсов и логов, поиск code smells, безопасный рефакторинг, перевод синтаксиса, ловушка «уверенного, но неверного» ответа.
    - *О чем:* гипотезы и их проверка, characterization-тесты, один шаг за итерацию, запреты на изменение поведения.

6. **Тестирование, тестовые данные и документация с ИИ.** Unit-тесты с моками и edge cases, тестовые данные, аудит «зелёных, но пустых» тестов, тесты для недетерминированных ИИ-функций (моки модели), docstrings, Swagger/OpenAPI.
   - *О чем:* генерация тестов и документации, проверка их качества и обязательная валидация того, что написал ИИ. Оценка качества ответов LLM (golden set, LLM-as-judge) — в блоке 3, тема 6; тестирование RAG-пайплайна — в блоке 4.

7. **Безопасность ИИ-кода и данных.** Захардкоженные секреты, инъекции, «галлюцинированные» зависимости, ПДн/NDA, ответственность за результат.
    - *О чем:* безопасная работа с публичными LLM, проверка сторонних библиотек, SAST/DAST, секреты в `.env`, лицензионная чистота.

## Блок 3. Программная интеграция LLM: API, инструменты, безопасность и экономика — 3 дня

1. **API, SDK, стриминг и сессии.** REST vs SDK, SSE, роли System/User/Assistant, хранение истории диалога, обрезка и суммаризация контекста.
   - *О чем:* жизненный цикл запроса к LLM из кода, разница между HTTP и SDK, стриминг для UI, архитектура сессий в БД.
   - *Зачем:* технический вход в блок: без этого Function Calling и MCP останутся теорией.

2. **Function Calling и Tool Use: как модель вызывает инструменты.** JSON Schema, `tool_calls`, parallel calls, валидация аргументов, human-in-the-loop, agent loop.
    - *О чем:* как дать ИИ «руки»: модель выбирает инструмент и аргументы, приложение выполняет код и возвращает результат; какие риски появляются.

3. **MCP: подключение внешних инструментов и данных.** Архитектура MCP, tools/resources/prompts, stdio и HTTP, auth, discovery, сравнение с Function Calling, supply chain.
    - *О чем:* как стандартизировать подключение БД, API, Jira, файловой системы и терминала; чем MCP отличается от function calling и когда он нужен.

4. **Безопасность LLM-приложений.** Prompt injection (direct/indirect), tool poisoning, excessive agency, output handling, guardrails, least privilege, sandbox, audit, red teaming и QA-тесты на инъекции.
    - *О чем:* trust boundaries агента, безопасность MCP-серверов, approved list, минимальные привилегии, ручное подтверждение деструктивных действий, проверка на непрямую промпт-инъекцию.

5. **Надёжность и наблюдаемость.** Rate limits (RPM/TPM), очереди, retry/backoff, circuit breaker, failover, логи, трейсы, стоимость и латентность на запрос, дрейф качества.
    - *О чем:* как не падать под нагрузкой, переключаться на резервную модель, видеть качество и стоимость в продакшене.

6. **Экономика и оценка качества (Evaluation).** Стоимость сессии, prompt caching, semantic cache, golden set, LLM-as-a-judge, регрессия при смене модели или промпта.
    - *О чем:* финансовый аудит ИИ-систем и автоматизированная проверка качества ответов.

## Блок 4. RAG — работа с корпоративными знаниями — 3 дня (без изменений)

1. **RAG vs Fine-Tuning.** Дообучение весов (дорого, долго, не гарантирует точность) против динамической подкладки контекста (дешево, быстро, гибко). Критерии выбора под бизнес-задачи.
    - *О чем:* Архитектурный выбор: когда нужно обучать нейросеть заново, а когда достаточно подкладывать нужные документы в контекст «на лету».

2. **Эмбеддинги и векторные базы данных.** Семантический поиск по смыслу; лёгкие решения «из коробки» (ChromaDB, FAISS), поиск по косинусному сходству.
    - *О чем:* Как ИИ ищет информацию не по ключевым словам, а по смыслу. Превращение текста в математические векторы и работа с векторными хранилищами.

3. **Chunking и сборка пайплайна.** Как нарезать документы, не теряя смысл; цепочка retrieve → augment → generate; формирование ответа со ссылкой на первоисточник.
    - *О чем:* Инженерия данных для ИИ. Правила разделения больших текстов на куски (чанки), алгоритм их поиска и склеивания в финальный промпт для генерации точного ответа.

### Почему Git остаётся отдельной темой

- Git — это **рабочий процесс**: изменения, коммиты, PR, ревью, откат.
- Безопасность — это **сквозное требование**, а не отдельный workflow. Если присоединить Git к безопасности, глава станет «2-в-1» и потеряет фокус.
- Code review шире безопасности: корректность, scope creep, тесты, поддерживаемость, лицензии.
- Блок 2 после изменений содержит 7 тем — место для отдельного Git-топика есть.

### Почему безопасность разделена на две темы

- **Блок 2, тема 7** — безопасность **кода и данных**: секреты, инъекции, зависимости, ПДн/NDA.
- **Блок 3, тема 4** — безопасность **LLM-приложений и агентов**: prompt injection, tool poisoning, excessive agency, MCP-права, guardrails, QA-тесты.
- Это позволяет не повторять одну и ту же мысль и не перегружать одну главу.

### Почему MCP после Function Calling

- Function Calling — это **механизм**: модель формирует `tool_calls`, приложение выполняет код.
- MCP — это **протокол**: как стандартизировать инструменты, ресурсы и права между клиентами и серверами.
- Сначала механизм, потом стандарт. Иначе студент подключает MCP-серверы, не понимая, что происходит под капотом.

### Почему API/SDK/сессии — тема 1 блока 3

- Это **предусловие** для Function Calling, MCP и оценки стоимости: нельзя вызвать инструмент, не умея сделать запрос и сохранить сессию.
- Блок 3 — про интеграцию в код, поэтому начинается с технического входа, а не с концепции инструментов.
- Перенос в конец блока 2 («мост от IDE к API») отвергнут: блок 2 — про ежедневную работу в IDE, API-интеграция туда не вписывается по фокусу.

### Почему «Тестирование, тестовые данные и документация» — в блоке 2, а не в блоке 4

Проверка на пересечения с блоком 4 (RAG) и блоком 3 (evals):

| Что проверяли | Блок 2, тема 6 | Блок 3, тема 6 | Блок 4 |
| :--- | :--- | :--- | :--- |
| Unit-тесты, моки, edge cases | да | нет | нет |
| Тестовые данные, аудит «зелёных, но пустых» тестов | да | нет | нет |
| Docstrings, Swagger/OpenAPI | да | нет | нет |
| Golden set, LLM-as-judge, регрессия качества | нет | да | нет |
| Оценка поиска RAG (Recall@K, MRR), Golden Set для чанкинга | нет | нет | да (тема 3) |

- В блоке 4 про тесты есть только **одна строка** — Golden Set как способ подобрать размер чанка, и один вопрос в пуле про метрики поиска. Это тестирование **RAG-пайплайна**, а не навык писать тесты и документацию.
- Пересечение было не между блоками, а **внутри формулировки** темы 6: там стояли `golden set`, `LLM-as-judge` и `red teaming`, которые уже есть в блоке 3, тема 6. Из блока 2 они убраны, чтобы не дублировать.
- `red teaming` перенесён в блок 3, тема 4 (QA-тесты на инъекции) — там он по смыслу.
- Итог: тема остаётся в блоке 2, потому что это ежедневный навык разработчика/QA — «ИИ пишет тесты и документацию, человек их проверяет», а не работа с корпоративной базой знаний.
